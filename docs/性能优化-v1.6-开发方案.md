## 0. 摘要

v1.4 的用户体感反馈集中在一句话：**"刚打开那几秒不流畅，用一会儿就顺了。"** 这不是偶发抖动，而是可量化的结构问题，两个根因叠加：

1. **包内没有有效的预热画像**：release APK 的 `assets/dexopt/baseline.prof` 解析后**只有 20 条规则，其中应用自身（`Lcom/buguake/**`）规则 0 条**；同时 `release { isMinifyEnabled = false }`（R8 全程关闭）。结果是安装时 AOT 只覆盖应用自己的类，**应用自己的 Composable 与数据层全靠运行时 JIT** —— 首帧要现场解释/编译一大片冷代码。
2. **首帧在主线程做同步 I/O**：共享偏好首次读取、Room 实例构建、**自定义背景图 JPEG 解码**、考试缓存 Keystore AES/GCM 解密 + JSON 解析，全部落在第一帧的组合期；随后数据分 5 批异步到达，每批都触发一次整树重组，把这批冷代码再各跑一遍。

v1.6 的主线就是把这两件事做掉，并顺手修掉一个由同一时间差引发的**真实功能缺陷**（首启/开机时提醒可能排不上，见 §1 B4 与 §3.4）。

- **本版主题**：启动与滚动流畅度（不改任何界面视觉、不改交互语义、不改既有数据结构）
- **版本落点**：v1.6（`versionCode 6 → 8`，`versionName "1.4" → "1.6"`，**跨过 v1.5**：若洗衣房先发则本版为 8；若两版合并发，本版落 7 并在 §9.2 按实际前序版本改写）
- **改动规模**：源码改动 7 个文件（13 处改动点）、新增 2 个单测；构建配置 2 处（`build.gradle.kts` + `proguard-rules.pro`）；文档 4 处（见 §10.B）
- **新增依赖**：运行时 **0**；构建期按 P0-1 可选 `androidx.baselineprofile` 插件 + `:baselineprofile` 模块（Macrobenchmark，仅本地/CI 生成画像用，不进 APK）
- **新增权限**：**0**
- **数据兼容**：无 Room schema 变更（`app/schemas/` 不动）、无既有 SharedPreferences key 改名；`EntryWithCourse.weeks` 只加内存缓存
- **可量化目标**：冷启动 `TotalTime` 中位数 **−30% 以上**；首屏（课表 tab）丢帧率 **< 5%**；启动期主线程同步 I/O **0 处**（§4 定义）
- **预估工时**：**4.2 人日**（含 R8 首开回归预算与真机测量，见 §7）
- **版本落点**：v1.6（§9 给出 6 处落点与核对清单）

### 1.1 已排除（不是瓶颈，避免误改）

- 桌面小组件与开机广播：三个 Provider 与 `BootReceiver` 均用 `goAsync()` + `Dispatchers.IO`（`widget/ScheduleWidgetProvider.kt:51-75`、`reminder/BootReceiver.kt:15`），无主线程阻塞。

- `AppDatabase.getInstance`（`data/AppDatabase.kt:76-85`）：Room 构建不打开数据库文件，本身不是主线程大头——**真凶是它被放进组合期（B2）**。

## 3. 详细设计

> 每个工作项给出：改哪里 / 怎么改 / 怎么验。行号基于 v1.4 源码，改动时以符号名为准。

### 3.1 P0-1：R8 与应用自身基线画像

**改哪里**：`ComposeApp/app/build.gradle.kts`（buildTypes.release）、新增 `ComposeApp/app/proguard-rules.pro` 内容（当前为空文件）、可选新增 `ComposeApp/baselineprofile/` 模块。

**怎么改**：

1. `release { isMinifyEnabled = true; isShrinkResources = true; proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro") }`。
2. 画像获取二选一，**本项目取 B（B 为终态，A 为过渡）**：
   - **A｜手工/真机过渡画像（先落地，0.5d）**：R8 关闭混淆名场景下，在 `app/src/main/baselineProfiles/baseline-prof.txt` 手写启动关键路径规则（`MainActivity`、`AppRoot`、`TimetableScreen`、`ScheduleSettings`、Room 生成的 `ScheduleDao_Impl`、`Glass` 等），`debug`/`release` 各自打包。缺点：需与代码同步维护，覆盖不精确。
   - **B｜Macrobenchmark 生成（推荐，1.0d）**：加 `androidx.baselineprofile` 插件 + `:baselineprofile` 模块（`androidx.benchmark:benchmark-macro-junit4`），在**真机**（本项目无 AVD，`benchmark` 支持 `CompilationMode.Partial` 真机采profile）跑冷启动 + 滚动用例，产出 `baseline-prof.txt` 落到 `app/src/main/baselineProfiles/` 并由 AGP 合并进包。
3. 复核产出的包：`app-release.apk` 的 `assets/dexopt/baseline.prof` 规则数与应用自身规则数（§10.A 步骤 3），**验收线：应用自身规则 > 0 且覆盖 `MainActivity`/`AppRoot`/`TimetableScreen`**。

**怎么验（必须做，不可省）**：R8 首开必做真机冒烟回归（§6.2），重点盯：
- `assets/html/about.html` + `privacy.html` 的 WebView 与 `AndroidBridge.post('checkUpdate')` 桥（`AboutPage.kt:63-99`）——JS 桥方法**只能靠 JS 调用，R8 会认为未使用**，必须 keep；
- `webimport/bridge/WebBridgeHandler.kt` 协议入口、Room 实体/DAO、`org.json` 反射式调用；
- 三个小组件与 `RemoteViews` 资源 id（资源压缩副作用）；
- 归档 `app/build/outputs/mapping/release/mapping.txt` 到 Release 附件（后续排查线上崩溃必需）。

**keep 规则起点**（写入 `proguard-rules.pro`，按实际回归增补）：

```proguard
# JS 桥：仅由 WebView 通过 addJavascriptInterface 反射调用
-keepclassmembers class * {
    @android.webkit.JavascriptInterface <methods>;
}
# Room：保留实体与 DAO（不整包 keep，尽量给 R8 留优化空间）
-keep @androidx.room.Entity class * { *; }
-keep @androidx.room.Dao interface * { *; }
-keep class * extends androidx.room.RoomDatabase { *; }
# 小组件 Provider 与广播接收器：由系统按类名实例化
-keep class com.buguake.timetable.widget.** { *; }
-keep class com.buguake.timetable.reminder.** { *; }
# org.json / OkHttp 反射与可选依赖
-dontwarn org.json.**
-dontwarn okhttp3.**
-dontwarn okio.**
```

> `-keep class com.buguake.timetable.data.**` 这种整包 keep 会显著削弱 R8 收益，**不作为默认规则**；仅在回归中确认真实缺失后再按具体类收窄补充。同理，若启用 `isShrinkResources` 后发现小组件布局资源被裁，按 `keep.xml` 精确白名单处理，不要整体关闭资源压缩。

### 3.2 P0-2：首帧主线程 I/O 清零

| 子项 | 现状 | 改法 | 验证 |
|---|---|---|---|
| 背景图解码 | `Glass.kt:110-113` 组合期 `decodeDownsampled(path, 1440)` | 目标态：`produceState<Bitmap?>(null, imagePath, stamp)` 在 `Dispatchers.IO` 解码，首帧先渲染既有内置渐变占位（该分支已存在，`Glass.kt:131-166`）；同时给进程级 `LruCache<String, Bitmap>`（key = path+mtime）避免每次进前台重解码 | 真机：冷启首帧无 `BitmapFactory` 主线程调用（可在 `decodeDownsampled` 前后打 `Looper.myLooper() == Looper.getMainLooper()` 断言日志，仅在 debug 构建启用） |
| Repository 构造 | `AppShell.kt:132-133` 组合期 `getInstance` | 目标态：`SettingsRepository.getInstance` 保留单例但**构造期不碰磁盘**——把 `readPrefs()`（`ScheduleSettings.kt:76`）与 `_settings` 初值改为"IO 线程首读 + `CompletableDeferred` 门闩"；`AppRoot` 用 `produceState` 拿首值；`loadExams()` 改 `produceState` | 冷启首帧 trace 中 `SharedPreferencesImpl`/`Keystore` 不在主线程 |

> 关键约束：`SettingsRepository` 的同步 API（`current`、`activeTimetableId`）被 `ClassReminderScheduler`、`ScheduleWidgetProvider`、`BootReceiver` 大量调用（`ClassReminderScheduler.kt:58,71,128,184`）。改造必须**新增** `suspend fun awaitReady()` 而不是把现有 getter 改成挂起，避免牵动小组件/接收器链路。

### 3.3 P1-2：启动数据"一次就绪"

**现状**：五路流（`AppShell.kt:135-144`）+ 空态入场动画（`TimetableScreen.kt:226-240`）→ 用户看到三次闪。

**改法**：
1. 在 `AppRoot` 加一个 `startupState`：`ensureActiveTimetableReady()` 完成 → 等 `activeTimetableIdFlow` 首个非 0 值 → 等 `observeAllEntries(id)` 首个非空（或"已查询完成"标志）→ 置 `ready=true`。
2. `ready=false` 时渲染**与首帧一致的骨架**：若沿用现有空态会引入新视觉，故改用"背景层 + 底部导航 + 课表格线骨架（不显示课程块）"，避免 §2.2 视觉变化红线。
3. 空态的"欢迎使用"入场动画保留，但只在 `ready && entries.isEmpty()` 时出现（真实新用户），不再在 `ready=false` 时抢先播放。

**验收**：录屏冷启动，`WELCOME` 空态**不再出现在已有数据的用户首屏**；`TimetableScreen` 在启动 1 秒内只组合 1 次正式网格（可用 `Modifier.layout` 或 debug 计数器验证）。

### 3.4 P1-3：提醒重排时序修复

**改法**（二选一，取 A）：
- **A（推荐）**：`AppShell.kt:496-506` 的 `LaunchedEffect` 改为先 `settingsRepo.awaitReady()`（新增，见 §3.2）再 `reschedule(context)`；`BootReceiver.kt:18` 同样先 `awaitReady()`。
- **B（兜底）**：`ClassReminderScheduler.reschedule/findNext` 内部改为 `settingsRepo.awaitActiveTimetableId()`，并在 `timetableId == 0L` 时**不提前返回**而是退化为"取库中第一张课表"。

**验收**（真机，必须做）：
1. 关闭应用 → `adb shell am force-stop` → 打开 → 立即 `adb shell dumpsys alarm | Select-String "buguake"`：应存在一条 `RTC_WAKEUP` 提醒（设置里 `remindEnabled=true`、且未来 28 天内有课）。
2. 重启手机（或 `adb shell am broadcast -a android.intent.action.BOOT_COMPLETED -p <pkg>`）后同样检查。
3. `ReminderDiagnostics`（`reminder/ReminderDiagnostics.kt`）记录的 `lastReschedule` 时间应在启动后 1 秒内且伴随 `next` 命中日志。

### 3.5 P2-1：`weeks` 缓存

**改法**：`data/ScheduleEntities.kt:91` 改为惰性缓存字段——非构造参数的成员加 `@Transient`（Kotlin 用 `@delegate:Transient` 打到 lazy 的委托字段上），`val weeks get() = weeksSet`。**不写库**，Room schema 不变；`equals/hashCode` 不受影响（data class 只按主构造参数生成）。

**验收**：新增单测 `ScheduleEntitiesWeeksTest`（`app/src/test/`）：同一实例连续 3 次 `weeks` 返回相等集合且仅解析 1 次（可注入计数或用 `weeksCsv` 变异检测缓存失效）；`testDebugUnitTest` 全绿。

### 3.6 P2-2：逐帧计算收敛（低风险，量力而行）

- `TimetableScreen.kt:172-176` 的 `maxEntryWeek`/`minWeek`/`maxWeek`：改 `remember(entries, examEntries, settings.totalWeeks)` 计算，避免每次重组重跑 `maxOfOrNull`。
- `TimetableScreen.kt:200-204`：`settledWeekState` 保持现状（它已用 `mutableStateOf` + `LaunchedEffect`），仅把 `selectedWeek` 读取改到 `derivedStateOf` 内，减少翻页期重组。

- `AppMotion.spatial()`：R8 + 画像落地后**重新评估**；若仍"跟手感偏软"，把 `StiffnessMediumLow → StiffnessMedium`（一行的可回退改动，单独提交便于 A/B）。

## 4. 度量协议（可量化目标与测量方法）

**测量环境**：真机（本仓库无 AVD，见 `DEVELOPMENT_ENVIRONMENT.md` §二）、release 签名包、**同一设备同一电量段**、息屏 30s 后测，每项 **≥5 次取中位数**。

> **基线已测（2026-09-19，v1.5 / versionCode 7 本地签名包，华为 PPG-AN00，课表有数据）**：
> - 冷启动 `TotalTime`：233 / 236 / 237 / 239 / 255 ms，**中位 239ms**（v1.6 目标 −30% → ≤167ms）
> - 启动期（冷启后前 ~2s）：21 帧，**丢帧 19.05%**，p50=6ms / p90=36ms / p95=93ms（尾部重帧与 B1/B2 吻合）

### 9.3 分支与提交策略

沿用 trunk-based + 特性分支隔离：

```
main ──●──────────────────────────●─── (tag v1.6)
        \                        /
         perf/v1.6-startup ─ 提交 1–9 ─ PR 合并
```

- 特性分支 `perf/v1.6-startup`；提交 1 为基线测量，**提交 9（版本号 + 更新记录）放最后**
- 收尾统一 bump（避免"尚未发布却已宣称 1.6"的中间态）
- 合并用 `git merge --no-ff`；合并后在 `main` 打 `v1.6`

### 9.4 升级与兼容

| 场景 | 结论 |
|---|---|
| v1.4 → v1.6 升级 | 无 schema/偏好迁移；首启仅多一次画像安装（系统 `dexopt`，属安装期，非启动期） |
| 首次启动新安装 | 基线画像在**安装时**由其 installer 应用（`profileinstaller`），首启即受益；未生效时行为与 v1.4 一致，不劣化 |
| 降级安装 | **不支持**（`versionCode` 只升不降）；回退须卸载重装，**会丢本地课表数据**（先导出） |
| 厂商 ROM 差异 | 国产 ROM 的"应用速冻/启动优化"可能让 JIT 缓存丢失，表现为"每次都慢"——基线画像正是对此的解法；若仍慢，按 §4 记录机型反馈 |

### 9.5 回滚与热修

- 版本号只升不降：出问题发 `v1.6.1`（`versionCode +1`）；不删 `v1.6` tag、不 force push。
- **可按提交单点回退**：R8（提交 7）与画像（提交 8）是**最后两个提交且互相独立**——若线上出现 R8 相关功能失效，`git revert` 提交 7 即可恢复 v1.4 行为，性能收益保留在提交 2–6。

### A. 复核命令（本次调研的实际用法，可原样复跑）

```powershell
# 1) 确认 release 是否开了 R8（看 isMinifyEnabled；并旁证 APK 内是否仍有 DebugProbesKt.bin）
Select-String -Path ComposeApp\app\build.gradle.kts -Pattern 'isMinifyEnabled|isShrinkResources'
Add-Type -AssemblyName System.IO.Compression.FileSystem
$zip='ComposeApp\app\build\outputs\apk\release\app-release.apk'
$z=[System.IO.Compression.ZipFile]::OpenRead($zip)
$z.Entries | Where-Object { $_.FullName -match 'dexopt|DebugProbes' } | Select-Object FullName,Length
$z.Dispose()

# 2) 合并画像里库规则 vs 应用自身规则
$f='ComposeApp\app\build\intermediates\combined_art_profile\release\compileReleaseArtProfile\baseline-prof.txt'
$all=Get-Content $f
"total=$($all.Count)  app=$((($all | Where-Object {$_ -match 'Lcom/buguake'})).Count)"

# 3) 解包 APK 内的画像规则数（二进制 .prof：以 'HSPL' 计数规则条数）
$tmp="$env:TEMP\bt_prof"; Remove-Item $tmp -Recurse -Force -ErrorAction SilentlyContinue
New-Item -ItemType Directory $tmp | Out-Null
Copy-Item $zip "$tmp\a.zip"
Add-Type -AssemblyName System.IO.Compression.FileSystem
[System.IO.Compression.ZipFile]::ExtractToDirectory("$tmp\a.zip","$tmp\x")
$c=Get-Content "$tmp\x\assets\dexopt\baseline.prof"
"rules=$($c.Count)  app=$((($c | Where-Object {$_ -match 'Lcom/buguake'})).Count)"

# 4) 冷启动与丢帧（真机，先 force-stop）
adb shell am force-stop com.buguake.timetable
adb shell am start -W -n com.buguake.timetable/.MainActivity

```
